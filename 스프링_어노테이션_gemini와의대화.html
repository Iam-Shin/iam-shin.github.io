✦ EntityManager.persist(obj)에 인자로 들어가는 객체 obj는 JPA 엔티티(Entity)여야 하며, 이를 위해서는 다음과 같은 자바 표준 스펙과 JPA 제약 사항을 지켜야 합니다.

  1. 필구 어노테이션
  • @Entity: 해당 클래스가 JPA가 관리하는 엔티티임을 명시해야 합니다. (예: Member, Order 클래스 상단)
  • @Id: 테이블의 기본 키(PK)와 매핑될 필드가 반드시 있어야 합니다. (예: private Long id;)
  1. 생성자 제약 (중요)
  • 기본 생성자(No-Arg Constructor)가 반드시 필요합니다.
  • 자바 스펙상 접근 제어자는 public 또는 protected여야 합니다. (private은 안 됨)
  • 프로젝트의 Order.java를 보면 @NoArgsConstructor(access = AccessLevel.PROTECTED)를 사용해 이 조건을 충족하고 있습니다. JPA가 지연 로딩(Proxy) 등을 구현할 때 이 생성자를 사용하기 때문입니다.
  1. 클래스 및 필드 제약
  • final 클래스를 사용할 수 없습니다. JPA는 성능 최적화를 위해 엔티티를 상속받는 프록시 객체를 생성하는데, final이 붙으면 상속이 불가능하기 때문입니다.
  • 마찬가지로 저장할 필드에 final을 사용할 수 없습니다.
  1. 식별자 상태
  • persist()를 호출하는 시점에 해당 객체는 비영속(New/Transient) 상태여야 합니다.
  • 즉, 데이터베이스에 아직 저장되지 않았고 영속성 컨텍스트에 포함되지 않은 순수한 객체 상태여야 합니다.

2 @Getter @Setter
3 public class Member {
4
5     @Id @GeneratedValue // 2. 식별자 필수
6     @Column(name = "member_id")

✦ JPA 학습의 시작이 막막하시다면, 가장 먼저 “객체가 데이터베이스에 저장되기까지의 생명주기(Lifecycle)”를 이해하는 것이 핵심입니다.

이 프로젝트의 InitDb.java 코드를 바탕으로, 데이터가 어떻게 생성되어 DB로 흘러가는지 4단계로 나누어 설명해 드릴게요.

1단계: 비영속 (New/Transient) - “순수한 자바 객체 상태”

먼저 메모리에 객체만 생성된 단계입니다. JPA나 데이터베이스와는 아무런 관련이 없습니다.

1 // InitDb.java의 createMember 메서드 내부
2 Member member = new Member(); // 1. 객체 생성
3 member.setName(name); // 2. 데이터 세팅
4 member.setAddress(new Address(city, street, zipcode));

  • 상태: 영속성 컨텍스트(EntityManager)가 이 객체의 존재를 모릅니다.
  • 특징: 이 상태에서 프로그램을 종료하면 데이터는 그냥 사라집니다.

2단계: 객체 간의 관계 맺기 (Association)

JPA는 객체 지향적으로 관계를 맺는 것을 중요하게 생각합니다. DB의 외래 키(FK)를 직접 다루는 게 아니라, 객체를 객체에 넣는 과정입니다.

1 // Order.java의 생성 메서드
2 public static Order createOrder(Member member, Delivery delivery, OrderItem... orderItems) {
3     Order order = new Order();
4     order.setMember(member);      // 주문과 회원 연결
5     order.setDelivery(delivery);  // 주문과 배송 연결
6     for (OrderItem orderItem : orderItems) {
7         order.addOrderItem(orderItem); // 주문과 상품들 연결
8     }
9     // ...

10 return order;
11 }

  • 이 과정에서도 아직 DB에는 아무런 변화가 없습니다. 단순히 메모리 상에서 객체들이 서로를 참조(Reference)하고 있는 상태입니다.

3단계: 영속 (Managed) - “JPA의 관리 시작”

이제 EntityManager에게 이 객체를 관리해달라고 맡기는 단계입니다.

1 // InitDb.java의 dbInit1 메서드
2 em.persist(member); // member 객체가 영속성 컨텍스트에 저장됨
3 em.persist(book1);
4 em.persist(order); // order와 연결된 delivery, orderItems도 같이 영속화됨 (Cascade 설정 덕분)

  • 무슨 일이 벌어지나?
    1. 객체가 영속성 컨텍스트(1차 캐시)라는 곳에 저장됩니다.
    2. JPA가 이 객체의 변경 사항을 감시하기 시작합니다.
    3. @GeneratedValue 설정이 있다면, 이 시점에 PK(ID) 값이 채워집니다.
  • 주의: 여전히 DB에 INSERT 쿼리가 날아간 상태는 아닙니다! (메모리에 쿼리를 쌓아두고 있습니다.)

4단계: 플러시 & 커밋 (Flush & Commit) - “DB 반영”

트랜잭션이 끝나는 시점에 JPA는 쌓아두었던 모든 변경 사항을 DB에 반영합니다.

1 // InitService 클래스에 붙은 @Transactional 어노테이션 덕분에
2 // 메서드 실행이 끝나면 자동으로 커밋이 일어납니다.

  • Flush: 영속성 컨텍스트의 변경 내용을 DB에 동기화 (SQL 전달).
  • Commit: DB의 트랜잭션을 실제로 확정.

💡 여기서 꼭 짚고 넘어가야 할 “기초 기술” 2가지

  1. 영속성 전이 (Cascade):
    Order.java를 보면 delivery와 orderItems 필드에 cascade = CascadeType.ALL이 붙어 있습니다. 이 덕분에 em.persist(order) 하나만 호출해도 연결된 배송 정보와 주문 상품들까지 줄줄이 사탕처럼 함께 저장되는 것입니다. (직접 일일이
    persist 할 필요가 없습니다.)

  2. 연관관계 편의 메서드:
    Order.java의 setMember(member) 메서드를 보면 member.getOrders().add(this) 처럼 양방향 객체 관계를 한 번에 세팅해 줍니다. “DB의 FK 관리자”가 누구인지 명확히 하면서도, “객체 세상의 양방향 연결”을 실수 없이 처리하기 위한
    기법입니다.

그런데 InitDb 는 어디서 호출되고 있지?

▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄▄
✦ InitDb는 누군가 명시적으로 “코드 한 줄”을 짜서 호출하는 것이 아니라, 스프링 프레임워크가 애플리케이션 시작 시점에 자동으로 호출합니다.

그 원리는 다음과 같습니다.

  1. @Component (빈 등록)
    InitDb 클래스 상단에 @Component가 붙어 있습니다. 스프링 부트가 실행될 때 컴포넌트 스캔을 통해 이 클래스를 찾아내고, 스프링 컨테이너에 객체(Bean)를 생성해서 등록합니다.

  2. @PostConstruct (초기화 메서드 실행)
    클래스 내부의 init() 메서드에 @PostConstruct가 붙어 있습니다.

1 @PostConstruct
2 public void init() {
3 initService.dbInit1();
4 initService.dbInit2();
5 }
이 어노테이션은 “스프링이 객체 생성을 끝내고 의존성 주입(initService 등)까지 완료한 직후에 이 메서드를 자동으로 실행해라”라는 약속입니다.

  1. 결론: 호출 주체는 ‘스프링’
    따라서 사용자가 애플리케이션을 실행(Run)하면, 스프링 부트가 뜨면서 내부적으로 다음과 같은 순서로 진행됩니다.
  2. InitDb 객체 생성
  3. initService 주입
  4. **init() 메서드 자동 호출

  • 활용법: 생성자를 직접 작성하지 않고도 생성자 주입(Constructor Injection)을 구현할 때 사용합니다. 이 파일에서는 initService와 EntityManager를 주입받기 위해 사용되었습니다.
  1. @PostConstruct
  • 제공자: Java/Jakarta EE (javax.annotation.PostConstruct)
  • 기능: 의존성 주입이 완료된 후, 해당 객체를 사용하기 전에 딱 한 번만 실행되어야 하는 초기화 로직을 지정합니다.
  • 활용법: init() 메서드에 적용되어, 스프링 빈인 InitDb가 생성되고 initService가 주입된 직후에 dbInit1(), dbInit2()를 호출하여 데이터를 초기화합니다.
  1. @Transactional
  • 제공자: Spring Framework (org.springframework.transaction.annotation.Transactional)
  • 기능: 해당 클래스나 메서드 내의 로직을 하나의 데이터베이스 트랜잭션으로 묶습니다. 성공하면 커밋(Commit), 예외가 발생하면 롤백(Rollback)을 수행합니다.
  • 활용법: JPA의 모든 데이터 변경은 트랜잭션 안에서 이루어져야 하므로, EntityManager를 사용하는 InitService에 필수적으로 적용되었습니다.

특이사항:
이 파일에서 InitDb와 InitService를 분리한 이유는 @PostConstruct와 @Transactional의 라이프사이클 차이 때문입니다. 스프링 빈의 초기화 시점(@PostConstruct)에는 트랜잭션 AOP가 아직 적용되지 않았을 수 있어, 별도의
빈(InitService)을 만들어 트랜잭션을 적용하고 이를 호출하는 방식을 사용한 것입니다.

✦ EntityManager.persist(obj)에 인자로 들어가는 객체 obj는 JPA 엔티티(Entity)여야 하며, 이를 위해서는 다음과 같은 자바 표준 스펙과 JPA 제약 사항을 지켜야 합니다.

  1. 필수 어노테이션
  • @Entity: 해당 클래스가 JPA가 관리하는 엔티티임을 명시해야 합니다. (예: Member, Order 클래스 상단)
  • @Id: 테이블의 기본 키(PK)와 매핑될 필드가 반드시 있어야 합니다. (예: private Long id;)
  1. 생성자 제약 (중요)
  • 기본 생성자(No-Arg Constructor)가 반드시 필요합니다.
  • 자바 스펙상 접근 제어자는 public 또는 protected여야 합니다. (private은 안 됨)
  • 프로젝트의 Order.java를 보면 @NoArgsConstructor(access = AccessLevel.PROTECTED)를 사용해 이 조건을 충족하고 있습니다. JPA가 지연 로딩(Proxy) 등을 구현할 때 이 생성자를 사용하기 때문입니다.
  1. 클래스 및 필드 제약
  • final 클래스를 사용할 수 없습니다. JPA는 성능 최적화를 위해 엔티티를 상속받는 프록시 객체를 생성하는데, final이 붙으면 상속이 불가능하기 때문입니다.
  • 마찬가지로 저장할 필드에 final을 사용할 수 없습니다.
  1. 식별자 상태
  • persist()를 호출하는 시점에 해당 객체는 비영속(New/Transient) 상태여야 합니다.
  • 즉, 데이터베이스에 아직 저장되지 않았고 영속성 컨텍스트에 포함되지 않은 순수한 객체 상태여야 합니다.

✦ JPA 학습의 시작이 막막하시다면, 가장 먼저 “객체가 데이터베이스에 저장되기까지의 생명주기(Lifecycle)”를 이해하는 것이 핵심입니다.

이 프로젝트의 InitDb.java 코드를 바탕으로, 데이터가 어떻게 생성되어 DB로 흘러가는지 4단계로 나누어 설명해 드릴게요.

1단계: 비영속 (New/Transient) - “순수한 자바 객체 상태”

먼저 메모리에 객체만 생성된 단계입니다. JPA나 데이터베이스와는 아무런 관련이 없습니다.

1 // InitDb.java의 createMember 메서드 내부
2 Member member = new Member(); // 1. 객체 생성
3 member.setName(name); // 2. 데이터 세팅
4 member.setAddress(new Address(city, street, zipcode));

  • 상태: 영속성 컨텍스트(EntityManager)가 이 객체의 존재를 모릅니다.
  • 특징: 이 상태에서 프로그램을 종료하면 데이터는 그냥 사라집니다.

2단계: 객체 간의 관계 맺기 (Association)

JPA는 객체 지향적으로 관계를 맺는 것을 중요하게 생각합니다. DB의 외래 키(FK)를 직접 다루는 게 아니라, 객체를 객체에 넣는 과정입니다.

1 // Order.java의 생성 메서드
2 public static Order createOrder(Member member, Delivery delivery, OrderItem... orderItems) {
3     Order order = new Order();
4     order.setMember(member);      // 주문과 회원 연결
5     order.setDelivery(delivery);  // 주문과 배송 연결
6     for (OrderItem orderItem : orderItems) {
7         order.addOrderItem(orderItem); // 주문과 상품들 연결
8     }
9     // ...

10 return order;
11 }

  • 이 과정에서도 아직 DB에는 아무런 변화가 없습니다. 단순히 메모리 상에서 객체들이 서로를 참조(Reference)하고 있는 상태입니다.

3단계: 영속 (Managed) - “JPA의 관리 시작”

이제 EntityManager에게 이 객체를 관리해달라고 맡기는 단계입니다.

1 // InitDb.java의 dbInit1 메서드
2 em.persist(member); // member 객체가 영속성 컨텍스트에 저장됨
3 em.persist(book1);
4 em.persist(order); // order와 연결된 delivery, orderItems도 같이 영속화됨 (Cascade 설정 덕분)

  • 무슨 일이 벌어지나?
    1. 객체가 영속성 컨텍스트(1차 캐시)라는 곳에 저장됩니다.
    2. JPA가 이 객체의 변경 사항을 감시하기 시작합니다.
    3. @GeneratedValue 설정이 있다면, 이 시점에 PK(ID) 값이 채워집니다.
  • 주의: 여전히 DB에 INSERT 쿼리가 날아간 상태는 아닙니다! (메모리에 쿼리를 쌓아두고 있습니다.)

4단계: 플러시 & 커밋 (Flush & Commit) - “DB 반영”

트랜잭션이 끝나는 시점에 JPA는 쌓아두었던 모든 변경 사항을 DB에 반영합니다.

1 // InitService 클래스에 붙은 @Transactional 어노테이션 덕분에
2 // 메서드 실행이 끝나면 자동으로 커밋이 일어납니다.

  • Flush: 영속성 컨텍스트의 변경 내용을 DB에 동기화 (SQL 전달).
  • Commit: DB의 트랜잭션을 실제로 확정.

💡 여기서 꼭 짚고 넘어가야 할 “기초 기술” 2가지

  1. 영속성 전이 (Cascade):
    Order.java를 보면 delivery와 orderItems 필드에 cascade = CascadeType.ALL이 붙어 있습니다. 이 덕분에 em.persist(order) 하나만 호출해도 연결된 배송 정보와 주문 상품들까지 줄줄이 사탕처럼 함께 저장되는 것입니다. (직접 일일이
    persist 할 필요가 없습니다.)

  2. 연관관계 편의 메서드:
    Order.java의 setMember(member) 메서드를 보면 member.getOrders().add(this) 처럼 양방향 객체 관계를 한 번에 세팅해 줍니다. “DB의 FK 관리자”가 누구인지 명확히 하면서도, “객체 세상의 양방향 연결”을 실수 없이 처리하기 위한
    기법입니다.

✦ InitDb는 누군가 명시적으로 “코드 한 줄”을 짜서 호출하는 것이 아니라, 스프링 프레임워크가 애플리케이션 시작 시점에 자동으로 호출합니다.

그 원리는 다음과 같습니다.

  1. @Component (빈 등록)
    InitDb 클래스 상단에 @Component가 붙어 있습니다. 스프링 부트가 실행될 때 컴포넌트 스캔을 통해 이 클래스를 찾아내고, 스프링 컨테이너에 객체(Bean)를 생성해서 등록합니다.

  2. @PostConstruct (초기화 메서드 실행)
    클래스 내부의 init() 메서드에 @PostConstruct가 붙어 있습니다.

1 @PostConstruct
2 public void init() {
3 initService.dbInit1();
4 initService.dbInit2();
5 }
이 어노테이션은 “스프링이 객체 생성을 끝내고 의존성 주입(initService 등)까지 완료한 직후에 이 메서드를 자동으로 실행해라”라는 약속입니다.

  1. 결론: 호출 주체는 ‘스프링’
    따라서 사용자가 애플리케이션을 실행(Run)하면, 스프링 부트가 뜨면서 내부적으로 다음과 같은 순서로 진행됩니다.
  2. InitDb 객체 생성
  3. initService 주입
  4. **init() 메서드 자동 호출

  • 제공자: Lombok (lombok.RequiredArgsConstructor)
  • 기능: final이 붙거나 @NonNull이 붙은 필드들을 파라미터로 받는 생성자를 자동으로 생성합니다.
  • 활용법: 생성자를 직접 작성하지 않고도 생성자 주입(Constructor Injection)을 구현할 때 사용합니다. 이 파일에서는 initService와 EntityManager를 주입받기 위해 사용되었습니다.
  1. @PostConstruct
  • 제공자: Java/Jakarta EE (javax.annotation.PostConstruct)
  • 기능: 의존성 주입이 완료된 후, 해당 객체를 사용하기 전에 딱 한 번만 실행되어야 하는 초기화 로직을 지정합니다.
  • 활용법: init() 메서드에 적용되어, 스프링 빈인 InitDb가 생성되고 initService가 주입된 직후에 dbInit1(), dbInit2()를 호출하여 데이터를 초기화합니다.
  1. @Transactional
  • 제공자: Spring Framework (org.springframework.transaction.annotation.Transactional)
  • 기능: 해당 클래스나 메서드 내의 로직을 하나의 데이터베이스 트랜잭션으로 묶습니다. 성공하면 커밋(Commit), 예외가 발생하면 롤백(Rollback)을 수행합니다.
  • 활용법: JPA의 모든 데이터 변경은 트랜잭션 안에서 이루어져야 하므로, EntityManager를 사용하는 InitService에 필수적으로 적용되었습니다.

특이사항:
이 파일에서 InitDb와 InitService를 분리한 이유는 @PostConstruct와 @Transactional의 라이프사이클 차이 때문입니다. 스프링 빈의 초기화 시점(@PostConstruct)에는 트랜잭션 AOP가 아직 적용되지 않았을 수 있어, 별도의
빈(InitService)을 만들어 트랜잭션을 적용하고 이를 호출하는 방식을 사용한 것입니다.

✦ EntityManager.persist(obj)에 인자로 들어가는 객체 obj는 JPA 엔티티(Entity)여야 하며, 이를 위해서는 다음과 같은 자바 표준 스펙과 JPA 제약 사항을 지켜야 합니다.

  1. 필구 어노테이션
  • @Entity: 해당 클래스가 JPA가 관리하는 엔티티임을 명시해야 합니다. (예: Member, Order 클래스 상단)
  • @Id: 테이블의 기본 키(PK)와 매핑될 필드가 반드시 있어야 합니다. (예: private Long id;)
  1. 생성자 제약 (중요)
  • 기본 생성자(No-Arg Constructor)가 반드시 필요합니다.
  • 자바 스펙상 접근 제어자는 public 또는 protected여야 합니다. (private은 안 됨)
  • 프로젝트의 Order.java를 보면 @NoArgsConstructor(access = AccessLevel.PROTECTED)를 사용해 이 조건을 충족하고 있습니다. JPA가 지연 로딩(Proxy) 등을 구현할 때 이 생성자를 사용하기 때문입니다.
  1. 클래스 및 필드 제약
  • final 클래스를 사용할 수 없습니다. JPA는 성능 최적화를 위해 엔티티를 상속받는 프록시 객체를 생성하는데, final이 붙으면 상속이 불가능하기 때문입니다.
  • 마찬가지로 저장할 필드에 final을 사용할 수 없습니다.
  1. 식별자 상태
  • persist()를 호출하는 시점에 해당 객체는 비영속(New/Transient) 상태여야 합니다.
  • 즉, 데이터베이스에 아직 저장되지 않았고 영속성 컨텍스트에 포함되지 않은 순수한 객체 상태여야 합니다.

2 @Getter @Setter

10 public Member() { }

✦ JPA 학습의 시작이 막막하시다면, 가장 먼저 “객체가 데이터베이스에 저장되기까지의 생명주기(Lifecycle)”를 이해하는 것이 핵심입니다.

이 프로젝트의 InitDb.java 코드를 바탕으로, 데이터가 어떻게 생성되어 DB로 흘러가는지 4단계로 나누어 설명해 드릴게요.

1단계: 비영속 (New/Transient) - “순수한 자바 객체 상태”

먼저 메모리에 객체만 생성된 단계입니다. JPA나 데이터베이스와는 아무런 관련이 없습니다.

1 // InitDb.java의 createMember 메서드 내부
2 Member member = new Member(); // 1. 객체 생성
3 member.setName(name); // 2. 데이터 세팅
4 member.setAddress(new Address(city, street, zipcode));

  • 상태: 영속성 컨텍스트(EntityManager)가 이 객체의 존재를 모릅니다.
  • 특징: 이 상태에서 프로그램을 종료하면 데이터는 그냥 사라집니다.

2단계: 객체 간의 관계 맺기 (Association)

JPA는 객체 지향적으로 관계를 맺는 것을 중요하게 생각합니다. DB의 외래 키(FK)를 직접 다루는 게 아니라, 객체를 객체에 넣는 과정입니다.

1 // Order.java의 생성 메서드
2 public static Order createOrder(Member member, Delivery delivery, OrderItem... orderItems) {
3     Order order = new Order();
4     order.setMember(member);      // 주문과 회원 연결
5     order.setDelivery(delivery);  // 주문과 배송 연결
6     for (OrderItem orderItem : orderItems) {
7         order.addOrderItem(orderItem); // 주문과 상품들 연결
8     }
9     // ...

10 return order;
11 }

  • 이 과정에서도 아직 DB에는 아무런 변화가 없습니다. 단순히 메모리 상에서 객체들이 서로를 참조(Reference)하고 있는 상태입니다.

3단계: 영속 (Managed) - “JPA의 관리 시작”

이제 EntityManager에게 이 객체를 관리해달라고 맡기는 단계입니다.

1 // InitDb.java의 dbInit1 메서드
2 em.persist(member); // member 객체가 영속성 컨텍스트에 저장됨
3 em.persist(book1);
4 em.persist(order); // order와 연결된 delivery, orderItems도 같이 영속화됨 (Cascade 설정 덕분)

  • 무슨 일이 벌어지나?
    1. 객체가 영속성 컨텍스트(1차 캐시)라는 곳에 저장됩니다.
    2. JPA가 이 객체의 변경 사항을 감시하기 시작합니다.
    3. @GeneratedValue 설정이 있다면, 이 시점에 PK(ID) 값이 채워집니다.
  • 주의: 여전히 DB에 INSERT 쿼리가 날아간 상태는 아닙니다! (메모리에 쿼리를 쌓아두고 있습니다.)

4단계: 플러시 & 커밋 (Flush & Commit) - “DB 반영”

트랜잭션이 끝나는 시점에 JPA는 쌓아두었던 모든 변경 사항을 DB에 반영합니다.

1 // InitService 클래스에 붙은 @Transactional 어노테이션 덕분에
2 // 메서드 실행이 끝나면 자동으로 커밋이 일어납니다.

  • Flush: 영속성 컨텍스트의 변경 내용을 DB에 동기화 (SQL 전달).
  • Commit: DB의 트랜잭션을 실제로 확정.

💡 여기서 꼭 짚고 넘어가야 할 “기초 기술” 2가지

  1. 영속성 전이 (Cascade):
    Order.java를 보면 delivery와 orderItems 필드에 cascade = CascadeType.ALL이 붙어 있습니다. 이 덕분에 em.persist(order) 하나만 호출해도 연결된 배송 정보와 주문 상품들까지 줄줄이 사탕처럼 함께 저장되는 것입니다. (직접 일일이
    persist 할 필요가 없습니다.)

  2. 연관관계 편의 메서드:
    Order.java의 setMember(member) 메서드를 보면 member.getOrders().add(this) 처럼 양방향 객체 관계를 한 번에 세팅해 줍니다. “DB의 FK 관리자”가 누구인지 명확히 하면서도, “객체 세상의 양방향 연결”을 실수 없이 처리하기 위한
    기법입니다.

✦ InitDb는 누군가 명시적으로 “코드 한 줄”을 짜서 호출하는 것이 아니라, 스프링 프레임워크가 애플리케이션 시작 시점에 자동으로 호출합니다.

그 원리는 다음과 같습니다.

  1. @Component (빈 등록)
    InitDb 클래스 상단에 @Component가 붙어 있습니다. 스프링 부트가 실행될 때 컴포넌트 스캔을 통해 이 클래스를 찾아내고, 스프링 컨테이너에 객체(Bean)를 생성해서 등록합니다.

  2. @PostConstruct (초기화 메서드 실행)
    클래스 내부의 init() 메서드에 @PostConstruct가 붙어 있습니다.

1 @PostConstruct
2 public void init() {
3 initService.dbInit1();
4 initService.dbInit2();
5 }
이 어노테이션은 “스프링이 객체 생성을 끝내고 의존성 주입(initService 등)까지 완료한 직후에 이 메서드를 자동으로 실행해라”라는 약속입니다.

  1. 결론: 호출 주체는 ‘스프링’
    따라서 사용자가 애플리케이션을 실행(Run)하면, 스프링 부트가 뜨면서 내부적으로 다음과 같은 순서로 진행됩니다.
  2. InitDb 객체 생성
  3. initService 주입
  4. **init() 메서드 자동 호출

    보통 스프링 부트 프로젝트에서는 src/main/resources/application.yml 파일에 이 설정이 들어있습니다.

✓ ReadFile src\main\resources\application.yml

✦ 현재 이 파일에서는 active: dev로 설정되어 있네요. 그렇다면 application-dev.yml 파일을 추가로 확인해야 합니다. 보통 개발 환경(dev)에서만 자동 생성을 활성화하기 때문입니다.

  1. application-dev.yml 확인

✓ ReadFile src...\application-dev.yml

✦ 찾았습니다! 이 파일의 다음 설정이 범인(?)입니다:

1 spring:
2 jpa:
3 hibernate:
4 ddl-auto: create # <— 이 설정!

누가, 어떻게 처리했나요?

  1. 누가?

    • Hibernate(하이버네이트)가 실제 작업을 수행합니다. JPA 구현체인 하이버네이트는 엔티티 클래스(@Entity가 붙은 클래스들)를 스캔하여 해당하는 CREATE TABLE 쿼리를 만들어 DB에 던집니다.
    • Spring Boot(스프링 부트)는 application-dev.yml에 있는 설정을 읽어 하이버네이트에게 “자동 생성을 하라”고 명령하는 역할을 합니다.

  2. ddl-auto: create의 의미

    • create: 애플리케이션을 실행할 때마다 기존 테이블을 몽땅 삭제(DROP)하고 새로 생성(CREATE)합니다.
    • 그래서 InitDb.java 같은 초기화 로직이 매번 실행되어도 데이터가 꼬이지 않고 항상 신선한(새로운) 상태로 시작할 수 있는 것입니다.

  3. 그 외 주요 옵션들 (참고)

    • update: 변경된 엔티티 정보만 DB 테이블에 반영 (칼럼 추가 등).
    • validate: 엔티티와 DB 테이블이 잘 매핑되어 있는지 확인만 함. (실무용)
    • none: 자동 생성 기능을 끔. (실무 운영 서버용)

결론:
application-dev.yml의 ddl-auto: create 설정 덕분에, 우리가 일일이 CREATE TABLE SQL을 짤 필요 없이 자바 엔티티 객체만 보고 Hibernate가 자동으로 DB 객체들을 생성해준 것입니다.
