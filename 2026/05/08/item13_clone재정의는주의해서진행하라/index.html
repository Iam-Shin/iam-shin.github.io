아이템 13. clone 재정의는 주의해서 진행하라

책을 다시 읽고 다시 이해해라 !!

  • 아래 내용은 Claude가 요약한 내용.

1. Cloneable 인터페이스의 이상한 설계

자바에서 복제를 하려면 Cloneable 인터페이스를 구현해야 할 것 같지만, 실제로는 이 인터페이스 안에 아무 메서드도 없다.

그런데 clone() 메서드는 Object 클래스에 있다.

이 구조가 왜 이상하냐면:

  • 보통 인터페이스를 구현한다 = 그 인터페이스의 메서드를 사용할 수 있다는 뜻
  • 그런데 Cloneable은 clone() 메서드를 선언하지 않고, Object.clone()의 동작 방식만 바꾼다
  • Cloneable을 구현한 클래스 → Object.clone()이 정상 동작
  • Cloneable을 구현하지 않은 클래스 → Object.clone() 호출 시 CloneNotSupportedException 발생

이건 인터페이스의 일반적인 용도와 다른, 매우 이례적인 사용법이다. 책에서는 이 설계를 “따라하지 말 것” 이라고 명시한다.

3. 불변 클래스에서의 clone() 구현

가장 단순한 경우: 모든 필드가 기본 타입(primitive)이거나 불변 객체인 클래스.

포인트:

  • super.clone()을 호출한다 — Object.clone()이 필드를 복사해준다
  • 반환 타입을 PhoneNumber로 좁혀서(공변 반환 타입) 호출하는 쪽에서 형변환 불필요
  • CloneNotSupportedException은 checked 예외인데, Cloneable을 구현했으므로 절대 발생하지 않는다 → AssertionError로 감싸서 무시

불변 필드만 있다면 이 정도로 충분하다. 하지만 가변 객체를 참조하는 필드가 있으면 큰 문제가 생긴다.

4. 가변 객체를 참조할 때의 문제 — 얕은 복사(Shallow Copy)

Stack 클래스 예시를 보자.

만약 단순히 super.clone()만 호출하면:

super.clone()은 elements 필드의 참조값만 복사한다. 즉, 원본과 복사본이 같은 배열 객체를 공유하게 된다.

이 상태에서 어느 한쪽을 수정하면 양쪽 모두 영향을 받는다. 이게 얕은 복사의 문제다.

5. 올바른 해결책 — 가변 필드는 따로 깊은 복사(Deep Copy)

elements.clone()은 배열을 새로 만들어 복사한다. 이제 원본과 복사본이 독립적인 배열을 가진다.

중요한 점:

  • elements 필드가 final이었다면 이 방법을 쓸 수 없다 (final 필드에는 새 값 대입 불가)
  • 이것이 clone()과 final 필드가 근본적으로 충돌하는 이유다

6. 더 복잡한 경우 — 배열 안에 또 가변 객체가 있을 때

HashTable 같은 자료구조를 생각해보자.

이 경우 buckets.clone()만 해서는 부족하다. 배열 자체는 새로 만들어지지만, 각 Entry 객체(연결 리스트)는 여전히 공유된다.

해결책: 연결 리스트를 재귀 또는 반복으로 깊은 복사

리스트가 길면 재귀 방식은 스택 오버플로가 날 수 있으므로 반복 방식이 더 안전하다.

7. clone() 구현 시 절대 하면 안 되는 것 — 재정의 가능한 메서드 호출 금지

clone() 내부에서 재정의될 수 있는 메서드를 호출하면 안 된다.

하위 클래스가 init()을 재정의했다면, 복제 과정에서 하위 클래스의 init()이 실행되어 원본과 복사본의 상태가 달라질 수 있다.

생성자에서도 마찬가지 원칙이 적용된다.

8. 상속용 클래스에서의 clone() 처리

상속을 허용하는 클래스(non-final)에서는 두 가지 선택이 있다.

선택 1 — Object처럼 동작하게 protected로 열어두기

하위 클래스가 Cloneable 구현 여부를 스스로 선택할 수 있도록 한다.

선택 2 — clone을 아예 막기

하위 클래스에서도 clone()을 사용하지 못하게 차단한다.

9. Cloneable을 구현한 스레드 안전 클래스

스레드 안전(thread-safe) 클래스에서 clone()을 구현한다면, 반드시 동기화(synchronized) 처리가 필요하다.

Object.clone()은 동기화를 고려하지 않으므로, 직접 처리해야 한다.

10. 결론 — 더 나은 대안: 복사 생성자 또는 복사 팩토리

위의 모든 문제들 때문에 책에서는 clone() 대신 복사 생성자나 복사 팩토리를 쓰라고 강력히 권장한다.

복사 생성자/팩토리의 장점:

항목 clone() 복사 생성자/팩토리
인터페이스 구현 필요 Cloneable 필수 불필요
예외 처리 CloneNotSupportedException 강제 없음
final 필드 할당 불가 문제 자유롭게 초기화
타입 유연성 같은 타입만 반환 인터페이스 타입 인자 가능
상속 안전성 하위 클래스에서 망가질 수 있음 안전

최종 요약

clone()은 처음부터 설계가 잘못된 메커니즘이다.
새로 클래스를 만든다면 복사 생성자나 복사 팩토리를 쓰는 게 훨씬 낫다.
배열을 복사할 때는 예외적으로 array.clone()이 깔끔하다.
기존 Cloneable 클래스를 확장해야 하는 경우에만 어쩔 수 없이 clone()을 구현하되, 가변 필드는 반드시 깊은 복사를 해라.
