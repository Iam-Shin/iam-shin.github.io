Effective Java 3Ed. item16.

아이템 16. public 클래스에서는 public 필드가 아닌 접근자 메서드를 사용하라

1. 퇴보한 클래스의 예

가끔 아래처럼 인스턴스 필드만 모아두는 것 외에 아무 목적이 없는 클래스를 작성하려 할 때가 있습니다.

이 클래스는 데이터 필드에 직접 접근할 수 있으니 캡슐화의 이점을 전혀 제공하지 못합니다.

2. public 필드가 나쁜 이유

public 필드를 직접 노출하면 다음과 같은 문제가 생깁니다:

  • API를 바꾸지 않고는 내부 표현을 바꿀 수 없다 (유연성 상실).
  • 불변식을 보장할 수 없다 — 클라이언트가 필드를 마음대로 바꿀 수 있다.
  • 필드에 접근할 때 부수 작업(로깅, 동기화 등)을 수행할 수 없다.

3. 올바른 방법: private 필드 + 접근자 메서드

public 클래스라면 필드를 모두 private으로 바꾸고, public 접근자(getter)와 변경자(setter) 메서드를 제공해야 합니다.

이렇게 하면:

  • 내부 표현을 언제든 바꿀 수 있다 (클라이언트는 메서드만 알면 됨).
  • setter에서 유효성 검사 등 부수 작업을 추가할 수 있다.
  • 불변식을 유지할 수 있다.

public 클래스가 필드를 공개하면, 그 필드를 사용하는 클라이언트가 생기고,
그 후에는 내부 표현을 바꾸기가 매우 어려워집니다.

4. 예외: package-private 또는 private 중첩 클래스

package-private 클래스 혹은 private 중첩 클래스라면 데이터 필드를 직접 노출해도 문제없습니다.

  • 패키지 외부 코드는 어차피 이 클래스에 접근할 수 없으므로, 표현을 바꿔도 패키지 안에서만 수정하면 됩니다.
  • private 중첩 클래스라면 그것을 감싼 클래스 안에서만 수정하면 됩니다.
  • 접근자 메서드를 강제할 때보다 오히려 코드가 더 간결하고 읽기 좋을 수 있습니다.

5. 불변 필드라면 덜 나쁘다 (하지만 여전히 좋지 않다)

public 필드가 불변(final)이라면, 직접 노출하더라도 그나마 덜 해롭습니다.
클라이언트가 값을 바꿀 수는 없으니 불변식은 보장됩니다.

그러나 이 경우에도:

  • API를 바꾸지 않고는 내부 표현을 바꿀 수 없습니다.
  • 필드 접근 시 부수 작업을 추가할 수 없습니다.

따라서 불변이라도 public 필드를 노출하는 것은 권장하지 않습니다.

6. 자바 플랫폼 라이브러리의 잘못된 예

java.awt 패키지의 Point와 Dimension 클래스는 public 필드를 직접 노출한 대표적인 반례입니다.

이미 수많은 코드가 이 필드에 직접 접근하고 있어서, 지금 와서 고칠 수가 없습니다.
특히 Dimension은 가변 필드를 노출한 탓에 성능 문제가 지금도 해결되지 않은 상태입니다.

이 클래스들은 “따라 하지 말아야 할 사례”로 유명합니다.

7. 핵심 정리

  • public 클래스는 절대 가변 필드를 직접 노출하지 마라.
  • 불변 필드라면 그나마 덜 해롭지만, 그래도 직접 노출하는 것은 권장하지 않는다.
  • package-private 클래스나 private 중첩 클래스는 필드를 직접 노출해도 된다.
