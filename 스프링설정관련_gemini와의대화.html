버전을 자주 바꿔야 한다면 간단한 .bat 파일을 만들어 사용하면 편리합니다.

  1. H2 Database에 대하여

결론부터 말씀드리면, 설치하시는 것이 훨씬 편리합니다.

  • 원리: H2는 자바로 작성된 아주 가벼운 DB입니다. 두 가지 방식으로 실행할 수 있습니다.
    • 임베디드(Embedded) 모드: 애플리케이션(스프링 부트)이 뜰 때 내부에서 같이 실행됩니다. 별도 설치가 필요 없지만,
      애플리케이션을 끄면 DB도 같이 꺼져서 데이터를 관리하기가 조금 번거롭습니다.
    • 서버(Server) 모드: 외부에서 DB를 따로 띄워놓고 애플리케이션이 여기에 접속하는 방식입니다. 실습하실 때는 이 방식을
      권장합니다. 애플리케이션을 껐다 켜도 데이터가 유지되고, H2 웹 콘솔을 통해 직접 SQL을 날려보며 확인하기 좋기 때문입니다.
  • 설치 위치: H2 사이트 (http://www.h2database.com)에서 다운로드하여 설치하거나 압축을 푼 뒤, bin/h2.bat(윈도우)을 실행하면 웹
    브라우저로 관리 창이 뜹니다.
  • 팁: 이 프로젝트(김영한 님의 강의 소스인 것 같네요!)는 보통 H2 1.4.200 버전을 기준으로 합니다. 최신 버전과 약간의 문법
    차이가 있을 수 있으니 버전을 맞춰 설치하는 것을 추천합니다.
  1. 외부 라이브러리(External Libraries)에 대하여

네, 처음 다운받은 소스 묶음에는 없었던 것들이 맞습니다.

  • 언제 다운로드 되었나?
    • 인텔리제이에서 프로젝트를 처음 열었을 때, 혹은 오른쪽 Gradle 탭에서 새로고침(Sync) 버튼을 눌렀을 때 다운로드됩니다.
    • 인텔리제이가 하단 상태 바에서 Importing Gradle project… 또는 Resolving dependencies… 라고 표시하며 열심히 게이지를
      채우던 단계가 바로 그 과정입니다.
  • 왜 소스에 포함하지 않나?
    • 용량 문제: 지금 ‘외부 라이브러리’에 있는 파일들을 다 합치면 수백 MB가 넘을 수 있습니다. 반면 소스 코드 자체는 몇 MB 안
      되죠.
    • 버전 관리: build.gradle에 “스프링 부트 2.4.1 써라”라고 명시만 해두면, 전 세계 어디서든 똑같은 버전을 인터넷에서
      내려받을 수 있습니다. 이것을 의존성 관리(Dependency Management)라고 합니다.
  • 어디서 받아오나?
    • build.gradle 파일 중간에 repositories { mavenCentral() } 이라는 설정이 있을 겁니다. mavenCentral은 전 세계 자바
      라이브러리들이 모여있는 거대한 인터넷 저장소입니다. Gradle이 여기서 필요한 파일들(.jar)을 자동으로 검색해서 가져옵니다.
  • 어디에 저장되나?
    • 프로젝트 폴더 안에 저장되지 않습니다. 컴퓨터의 사용자 홈 디렉토리(보통 C:\Users\사용자.gradle\caches)라는 공용
      저장소에 저장됩니다.
    • 이유: 내 컴퓨터에 프로젝트가 10개 있어도, 똑같은 스프링 라이브러리는 딱 한 번만 다운로드해서 공유하기 위해서입니다.
      (프로젝트마다 수백 MB씩 중복 저장하면 하드디스크가 금방 꽉 차겠죠?)

  1. H2 DB는 별도로 설치해서 실행해두는 것이 공부하시기에 훨씬 좋습니다 (데이터 확인용).
  2. 외부 라이브러리는 build.gradle이라는 명세서에 따라 Gradle이 인터넷에서 자동으로 쇼핑해온 결과물입니다.

방법 A: 스프링 부트 ‘내장(Embedded)’ 모드 사용 (가장 추천)
별도의 DB 서버를 띄우지 않고, 애플리케이션이 실행될 때 메모리나 로컬 파일에 DB를 함께 띄우는 방식입니다.

  1. src/main/resources/application.yml 파일을 엽니다.
  2. datasource 설정을 아래와 같이 확인하거나 수정합니다.
1     spring:
2       datasource:
3         url: jdbc:h2:mem:testdb  # 메모리에 DB를 생성 (재시작하면 초기화됨)
4         # 또는 jdbc:h2:~/jpashop (내 홈 디렉토리에 파일로 저장)
5         driver-class-name: org.h2.Driver
6         username: sa
7         password:
8       h2:
9         console:

10 enabled: true # 웹 브라우저에서 DB를 볼 수 있게 함
3. 애플리케이션(JpashopApplication.java)을 실행합니다.
4. 브라우저에서 http://localhost:8080/h2-console에 접속하면 설치 없이도 DB 관리 창이 뜹니다. (이때 JDBC URL을 위 설정과

  1. build.gradle: 프로젝트의 설계도이자 명세서

이 파일은 “이 프로젝트를 어떻게 빌드(컴파일, 패키징)하고, 어떤 외부 라이브러리를 가져올 것인가?”를 결정합니다.

주요 섹션별 의미 (현재 파일 기준)

  • plugins { … }: Gradle에게 “이 프로젝트는 스프링 부트 프로젝트이고, 자바 프로젝트야”라고 가르쳐주는 도구 모음입니다.
  • sourceCompatibility = ‘11’: “이 코드는 자바 11 문법으로 작성되었으니, 자바 11로 컴파일해줘”라는 뜻입니다.
  • repositories { mavenCentral() }: “필요한 라이브러리는 전 세계 표준 저장소인 Maven Central에서 찾아와”라는 선언입니다.
  • dependencies { … }: 가장 중요한 ‘장바구니’입니다.
    • implementation: 실제 코드를 짤 때와 실행할 때 모두 필요한 라이브러리 (Spring Data JPA, Thymeleaf 등).
    • compileOnly: 코드를 짤 때(컴파일)만 필요하고, 실행 파일(.jar)에는 포함 안 시켜도 되는 것 (Lombok - 컴파일 때 코드를
      대신 생성해주니까요).
    • runtimeOnly: 코드를 짤 때는 필요 없지만, 프로그램을 실행할 때만 필요한 것 (H2 DB 드라이버 - 소스 코드에서 DB 드라이버를
      직접 호출하진 않죠).
  1. application.yml: 애플리케이션의 설정값 (런타임 제어)

이 파일은 “프로그램이 돌아가는 도중에 참조할 변수값들”을 모아놓은 곳입니다. .properties 방식보다 계층 구조(Tree)로 되어 있어
가독성이 좋습니다.

주요 설정의 의미와 원리

  • spring.datasource: DB 연결 정보입니다.
    • url: “어디에 있는 DB에 접속할까?”
    • username/password: “어떤 계정으로 접속할까?”
  • spring.jpa.hibernate.ddl-auto: JPA의 핵심 기능입니다.
    • create: “시작할 때 기존 테이블 다 지우고 새로 만들어!” (개발용)
    • none 또는 validate: “실제 운영 서버니까 테이블 건드리지 마!” (운영용)
  • spring.jpa.show-sql: true: “JPA가 내부적으로 만드는 SQL을 콘솔창에 보여줘.” (학습/디버깅용)

✦ 네, 정확합니다! Spring Initializr는 프로젝트의 ‘뼈대’를 자동으로 생성해 주는 아주 강력한 도구입니다.

선택한 사항들이 build.gradle의 dependencies에 들어가는 것은 물론이고, 그 외에도 현대적인 자바 개발에서 필수적인 여러 설정들을
자동화해 줍니다. 구체적으로 어떤 것들을 해주는지 원리와 함께 설명해 드릴게요.

  1. ‘Starter’ 의존성 조합 (가장 핵심적인 자동화)

단순히 라이브러리 한두 개를 추가하는 게 아닙니다. 스프링 부트는 ‘Starter’라는 개념을 사용합니다.

  • 원리: 예를 들어 Spring Web을 선택하면 build.gradle에 spring-boot-starter-web 하나가 추가됩니다. 그런데 이 ‘Starter’ 하나가
    내부적으로 Tomcat(서버), Jackson(JSON 변환), Spring MVC, Logging 등 수십 개의 관련 라이브러리를 서로 궁합이 맞는 버전으로
    묶어서 가져옵니다.
  • 이유: 예전에는 수십 개의 .jar 파일 버전을 일일이 맞추다가 충돌이 나면 해결하는 데만 며칠이 걸렸습니다. Initializr는 이 버전
    조합(Version BOM)을 완벽하게 세팅해 줍니다.
  1. 표준 디렉토리 구조 생성 (Convention over Configuration)

자바 진영의 표준인 Maven/Gradle 디렉토리 구조를 자동으로 만들어 줍니다.

  • 구조: src/main/java, src/main/resources, src/test/java 등.
  • 원리: “설정보다 관습(Convention over Configuration)”이라는 철학에 따라, 정해진 위치에 코드를 두면 스프링이 별도 설정 없이도
    코드를 찾아 실행합니다.
  • 자동화 내용: 패키지 경로(예: com.example.demo)까지 폴더로 다 생성해 줍니다.
  1. 메인 애플리케이션 클래스 생성 (@SpringBootApplication)

프로그램의 시작점인 Main 클래스를 자동으로 작성해 줍니다.

  • 자동화 내용:

1 @SpringBootApplication
2 public class DemoApplication {
3 public static void main(String[] args) {
4 SpringApplication.run(DemoApplication.class, args);
5 }
6 }

  • 이유: 이 클래스 하나가 컴포넌트 스캔(빈 등록), 자동 설정(Auto Configuration), 내장 서버 구동을 모두 시작하는 방아쇠 역할을
    합니다.
  1. Gradle Wrapper (gradlew) 포함

이게 정말 중요한데, 내 컴퓨터에 Gradle이 설치되어 있지 않아도 빌드할 수 있게 해줍니다.

  • 원리: 프로젝트 폴더 안에 gradlew (유닉스용), gradlew.bat (윈도우용) 파일을 넣어줍니다.
  • 이유: “내 컴에선 되는데 왜 니 컴에선 안 돼?”라는 문제를 방지하기 위해서입니다. 이 파일을 실행하면 설정된 버전의 Gradle을
    알아서 다운로드해서 빌드합니다. (팀원 모두가 동일한 환경을 유지하게 됨)
  1. .gitignore 자동 생성

Git 같은 버전 관리 시스템에 올려야 할 것과 올리지 말아야 할 것을 미리 구분해 줍니다.

  • 자동화 내용: 빌드 결과물(build/), IDE 설정 파일(.idea/), 로그 파일 등을 자동으로 제외 목록에 넣어줍니다.
  • 관습: 소스 코드만 공유하고 무거운 라이브러리나 개인 설정은 공유하지 않는 것이 관습입니다.

실무적인 팁: 왜 Initializr를 쓰나요?

수동으로 build.gradle을 만들 수도 있지만, Initializr를 쓰는 이유는 “실수를 줄이기 위해서”입니다.

  1. 버전 호환성: 스프링 부트 버전과 각 라이브러리 버전 사이의 미묘한 충돌을 피할 수 있습니다.
  2. 최신 트렌드 반영: 자바 버전이나 스프링의 최신 권장 설정을 즉시 적용할 수 있습니다.

요약하자면:
Spring Initializr는 “명세서(Metadata)”를 작성하면 “완성된 공장(Project 구조)”을 통째로 지어주는 서비스라고 생각하시면 됩니다.

이제 이 프로젝트의 build.gradle을 다시 보시면, dependencies 섹션의 이름들이 spring-boot-starter-xxx로 시작하는 이유를 이해하실
수 있을 겁니다! 더 궁금한 설정이나 구조가 있으신가요?

  1. 로컬에서 서버로 보낼 결과물 (Artifact)

스프링 부트는 ‘Executable Jar’ (Fat Jar) 방식을 사용합니다. 애플리케이션 실행에 필요한 모든 라이브러리와 내장 서버(Tomcat)가
하나의 파일에 포함되어 있습니다.

  • 생성 방법: 프로젝트 루트 디렉토리에서 다음 명령어를 실행합니다.
    • ./gradlew clean build (또는 gradlew.bat build on Windows)
  • 결과물 위치: build/libs/ 폴더 안에 생성되는 [프로젝트명]-[버전].jar 파일 하나만 서버로 복사하면 됩니다. (보통 -plain.jar가
    붙지 않은 더 큰 용량의 파일을 사용합니다.)
  • 전송 도구: scp, sftp, FTP 등을 이용해 서버의 특정 디렉토리로 업로드합니다.
  1. 서버 측 준비 환경

서버에는 복잡한 설정이 필요 없지만, 최소한 다음은 갖춰져야 합니다.

  • JRE(Java Runtime Environment) 또는 JDK:
    • 로컬에서 프로젝트를 빌드할 때 사용한 자바 버전(현재 프로젝트는 Java 11)과 동일하거나 상위 버전의 JRE가 설치되어 있어야
      합니다.
    • java -version 명령어로 설치 여부와 버전을 확인합니다.
  • 운영체제(OS): Linux(Ubuntu, CentOS 등)가 표준이지만 Windows Server도 가능합니다.
  • 방화벽 설정:
    • 애플리케이션이 사용할 포트(기본값 8080)가 외부에서 접속 가능하도록 열려 있어야 합니다.
  • 디렉토리 구조:
    • /home/user/app/ 처럼 배포 파일을 보관할 전용 폴더를 만드는 것이 관리에 용이합니다.
  1. 배포 시 관여하는 주요 설정값 (Configuration)

운영 서버는 로컬 PC와 환경(DB 주소, 비밀번호, 포트 등)이 다르므로 이를 분리해야 합니다.

  • 외부 설정 주입 (Profile):
    • src/main/resources/application-prod.yml 파일을 만들어 운영 서버 전용 설정을 작성합니다.
    • 서버에서 실행 시 다음과 같이 명령어를 입력하여 운영 설정을 적용합니다.

1 java -jar -Dspring.profiles.active=prod your-app-name.jar

  • 핵심 설정 항목:
    • server.port: 운영 서버에서 서비스할 포트 번호.
    • spring.datasource.url: 실제 운영 DB의 접속 주소(JDBC URL).
    • spring.jpa.hibernate.ddl-auto: 반드시 none 또는 validate로 설정해야 합니다. (로컬처럼 create를 쓰면 서버 시작 시 운영
      데이터가 모두 삭제될 수 있어 매우 위험합니다.)
    • logging.level: 운영 환경에서는 로그 양을 줄이기 위해 INFO 또는 WARN으로 설정하는 것이 일반적입니다.

  1. 운영 설정으로 로컬 서버를 켜는 방법 (Technical)

그 이유를 3가지 측면에서 설명해 드릴게요.

  1. H2 In-memory DB의 특성 (mem)
    H2의 mem 방식은 메모리 상에 데이터베이스를 생성합니다. URL에 적어준 이름(jpashop-prod)은 단순히 해당 메모리 영역의 “이름표”일
    뿐입니다.
  • 결과: 해당 이름의 DB가 없으면 H2가 실행 시점에 자동으로 새로 만듭니다. 따라서 “DB를 찾을 수 없다”는 오류는 나지 않습니다.
  1. ddl-auto: validate와의 충돌 (핵심 오류 원인)
    앞서 제가 제안해 드린 application-prod.yml 설정에는 ddl-auto: validate가 들어있을 것입니다.
  • 상황: 메모리 DB(mem)는 서버를 켤 때마다 텅 빈 상태로 시작됩니다.
  • 충돌: 서버가 켜지면서 JPA가 운영 DB(텅 빈 메모리)를 검토합니다. “어? Member 테이블이 있어야 하는데 하나도 없네?”라고
    판단합니다.
  • 결과: SchemaManagementException이 발생하며 서버 기동이 중단됩니다. 운영 환경(prod)에서는 데이터가 미리 있어야 한다고
    가정하기 때문입니다.
  1. 운영 환경에서 mem 사용의 모순
    실제 운영 환경(prod)에서 jdbc:h2:mem을 사용하는 경우는 거의 없습니다.
  • 이유: 서버를 재시작하는 순간 모든 운영 데이터(주문 내역, 회원 정보 등)가 영구적으로 삭제되기 때문입니다.

  • (참고: 예전 버전의 경우 jpashop.h2.db나 jpashop.trace.db 파일이 함께 생기기도 합니다.)
  1. ddl-auto: create 설정의 효과
    이 설정을 하고 서버를 실행하면 다음과 같은 일이 일어납니다.
  2. 파일 생성: 지정된 경로에 jpashop.mv.db 파일이 없으면 새로 만듭니다.
  3. 테이블 초기화: 만약 기존에 테이블이 있었다면 모두 DROP(삭제)한 뒤, 엔티티 클래스 정보를 바탕으로 테이블을 새로
    생성(CREATE)합니다.
  4. 데이터 보존: 서버를 종료해도 파일(jpashop.mv.db)은 그대로 남습니다. 하지만 다음에 서버를 다시 켤 때 create 옵션 때문에
    기존 데이터는 모두 지워지고 테이블이 다시 만들어집니다.

[팁] 데이터를 계속 유지하고 싶다면?
테이블 구조가 잡힌 후에는 ddl-auto 설정을 다음과 같이 변경해 보세요.

  • none 또는 validate: 테이블을 건드리지 않고 파일에 저장된 데이터를 계속 유지합니다.
  • update: 기존 데이터는 유지하면서, 엔티티에 새로 추가된 필드만 테이블에 반영합니다. (단, 운영 환경에서는 권장하지 않습니다.)

결론: 지금 바로 윈도우 탐색기를 열어 C:\Users\본인계정\ 폴더를 확인해 보시면 jpashop.mv.db 파일이 생성되어 있는 것을 보실 수
있을 겁니다!
