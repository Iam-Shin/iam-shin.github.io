Effective Java 3Ed. item12.

아이템 12. toString을 항상 재정의하라

- Object 의 기본 toString은 단순히 클래스명@16진수해시코드 형태다.

  • 읽기 쉽고 유용한 정보를 보여주도록 재정의 하자
  • phoneNUmber라면 ‘phoneNumber: Henry=010-1234-5678’

- Collection 또는 정보량이 많을경우 Summary 를 보여주는것도 좋다

  • “맨해튼 전화번호부 (총 2299000개)

- 중요한 정보는 충분히 담아라.

  • 잘못된 예: “단언실패 : 기대값 {abc, 123}, 결과값 {abc, 123}”
  • toString 메세지를 보고 혼란 유발. (클래스타입을 추가하거나, 인스턴스 해시코드를 추가해야하지 않을까)

- 포멧을 명시하든 아니든, 그 의도를 명확히 밝혀라.

- toString이 반환한 값에 포함된 정보를 얻어올 수 있는 API 를 제공하라

  • toString의 반환값을 파싱해야 값을 얻을수 있는 상황을 만들지 말라
  • phoneNumber 라면 getAreaCode, getPrefix, getMemberNUmber 같은 접근자를 제공하자.

- 하위 컬랙션이 공유해야할 문자열 표현이 있는 추상클래스라면 toString을 재정의 해줘라.

Effective Java 3Ed. item10.

아이템 10. equals는 일반 규약을 지켜 재정의하라

이번장은 내용이 많다. 여러번 다시 읽을 필요가 있다.

- equals를 재정의 하지 말아야할 이유

  • 각 인스턴스가 본질적으로 고유하다
  • 인스턴스의 ‘논리적 동치성’ 을 검사할 일이 없다. (Object의 기본 equals 만으로도 해결)
  • 상위클래스에서 재정의한 equals가 하위클래스에서도 딱 들어맞는다.
  • 클래스가 private 이거나, package-private이고 equals 메서드를 호출할 일이 없다.

- 그렇다면 equals 를 재정의 해야할 때는?

  • 객체식별성(두 객체가 물리적으로 같은가?)이 아니라, 논리적 동치성을 확인해야 하는데, 상위클래스의 equals가 논리적 동치성을 비교하도록 정의되지 않았을때.

- equals 메서드를 재정의할때 반드시 따라야할 일반규약

  • 반사성(reflexivity) : not null인 reference x에 대해(이하 생략) x.equals(x) = true 이다.
  • 대칭성(symmetry) : x,y에 대해 x.equals(y) = true 면 y.equals(x) = true 이다.
  • 추이성(transitivity) : x,y,x에 대해 x.equals(y) = true 이고 y.equals(z) = true 면 x.equals(z) = true 이다.
  • 일관성(consistency) : x,y에 대해 x.equals(y) 의 결과는 반복 수행되더라도 항상 true 이거나, 항상 false 이다.
  • null-아님 : x.equals(null) 은 false 이다.

- 양질의 equals 메서드를 구현하는 방법

  1. == 연산자를 사용해 입력이 자기 자신의 참조인지 확인한다.
  2. instanceof 연산자로 입력이 올바른 타입인지 확인한다.
  3. 입력을 올바른 타입으로 형변환한다.
  4. 입력객체와 자기 자신의 대응되는 핵심 필드들이 모두 일치하는지 하나씩 검사한다.

- 그리고, 테스트를 위한 AutoValue 프레임워크가 있다.

Effective Java 3Ed. item68.

아이템 68. 일반적으로 통용되는 명명 규칙을 따르라

[JLS, 6.1] 에 명명규칙이 잘 정리되어 있다.

- 패키지, 모듈이름

  • 조직의 인터넷 도메인이름의 역순
  • 각 요소는 대체로 8자 이내의 짧은 단어, 약자허용

- 클래스, 인터페이스

  • 대문자로 시작, 카멜케이스
  • 약자 지양 full단어
  • 객체를 생성할 수 있는 클래스의 이름은 보통 단수명사나 명사구 사용: Thread, PriorityQueue 등
  • 객체를 생성할 수 없는 클래스는 복수형명사로 : Collectors, Collections 등
  • 인터페이스는 클래스와 똑같이 짓거나 able , ible 로 끝나는 형용사 : Runnable, Iterable 등
  • 애너테이션은 규칙없이 다양

- 메서드, 필드

  • 클래스 명명규칙과 동일하지만 첫글자는 소문자
  • 상수필드는 full 대문자, 단어사이는 _ 언더바
  • 동사나 목적어를 포함한 동사구 사용 : append, drawImage
  • boolean 을 리턴하는 메서드는 보통 is , has 로 시작
  • boolean이 아닌경우 명사, 명사구, get속성, set속성 : size, hashCode, getTime, setTime 등
  • 객체 타입변경시 to목적타입 : toString, toArray 등
  • 객체의 내용을 다른 뷰로 보여주는 경우 as타입 : asList 등
  • 객체값을 원시타입으로 변경하는 경우 타입Value 형태로 : intValue, longValue
  • 정적팩터리 : from, of, valueOf, instance, getInstance, newInstance, getType, newType

- 지역변수

  • 소문자. 약어 가능

타입 매개변수

  • 보통 한문자 대문자로 표현
  • T:타입, E:컬랙션의 원소, K,V:맵의 키와 밸류, X:예외, R:메서드의 반환타입, U,V,T1,T2..:그외 임의타입

Effective Java 3Ed. item67.

아이템 67. 최적화는 신중히 하라

- 최적화 격언 세가지

  1. 그 어떤 핑계보다 효율성 이라는 이름아래 행해진 컴퓨팅 죄악이 더 많다.(심지어 효율을 높이지도 못하면서)
  2. (전체의 97% 정도인) 자그마한 효율성은 모두 잊자. 섣부른 최적화가 만악의 근원이다
  3. 최적화를 할때는 다음 두가지 규칙을 따르라.
  • 첫번째, 하지마라
  • 두번째, (전문가 한정)아직 하지마라

섣부른 최적화는 자칫 견고한 구조설계를 파괴하고도 높은 성능개선을 이루지 못한다는 것.

이하 내용의 상세 설명은 이해될때 추가할것.

- 빠른프로그램 보다는 좋은 프로그램을 작성하라

- 성능을 제한하는 설계를 피하라

  • 특히 변경이 어려운 요소들. 컴포넌트간/시스템간 외부소통 프로토콜. API, 네트워크, 영구 저장데이터포멧 등

- API를 설계할때 성능에 주는 영향을 고려하라

- 성능을 위하여 API를 왜곡하지 마라

- 각각의 최적화 시도 전후로 성능을 측정하라

- 알고리즘부터 재검토하라

Effective Java 3Ed. item66.

아이템 66. 네이티브 메서드는 신중히 사용하라

- 자바 네이티브 메서드란?

  • native 키워드를 사용하여, java 가 아닌 C, C++ 같은 다른 프로그래밍언어(네이티브코드) 로 구현된 함수를 java 코드에서 직접 호출하는 메서드.

- 목적

  1. 레지스트리등 플랫폼 특화기술
    Java -> JNI -> OS API (Win32 API, POSIX) -> 하드웨어/커널
  2. 레거시 C, C++ 라이브러리 활용
  3. 성능 크리티컬한 부분을 C로 최적화 (요즘엔 vm 성능이 극적으로 향상되어, 유명무실.)

- 단점

  1. 메모리 안전성 파괴
  2. 플랫폼 독립성 상실
  3. 디버깅 난이도 급상승
  4. GC와의 상호 작용 복잡성

- 대안

  1. Panama API로 JNI 완전 대체
  2. 성능 측정후 결정하는 원칙
  3. GraalVM Native Image로 네이티브 필요성 제거

- JNI는 Java의 안전망에 구멍을 뚫는다. 현대 Java는 그 구멍을 하나씩 메우고 있다.

Effective Java 3Ed. item65.

아이템 65. 리플렉션보다는 인터페이스를 사용하라

- 리플렉션이란? java.lang.reflection

  • 프로그램이 자기자신의 구조를 런타임에 조사하고 조작하는 기능

- 리플렉션의 단점

  1. 컴파일 시점에 타입 검사 불가
  1. 장황하고 복잡한 코드: Exception만 붙여도 6종.
    ClassNotFoundException NoSuchMethodException IllegalAccessException
    InstantiationException InvocationTargetException ClassCastException …
  2. 성능저하 - 아래 과정을 매번 거침.
    invoke() 호출 -> 접근권한 검사(isAccessible?) -> 파라미터 타입 검증
    -> 오토박싱 (primitive -> Object) -> 실제 메서드 디스패치 -> 결과 언박싱

- 리플렉션의 활용

  • 컴파일시에는 알수 없고, 런타임에 존재하지 않을수도 있는 다른 클래스, 메서드의 의존성 판단시
  • 버전이 여러개인 외부 클래스의 의존성 선택.

- 대안

  • 생성만 리플렉션, 생성 이후에 사용할때는 인터페이스나 상위클래스로 형변환해서 사용.
  • 참고!! 코드65-1 참조할것. 제너릭 Set 성능 분석 도구로 활용할 수 있음.

Effective Java 3Ed. item64.

아이템 64. 객체는 인터페이스를 사용해 참조하라

- 구현 클래스 타입이 아닌 인터페이스 타입으로 변수를 선언하라.

  • 다형성에 기반한 교체 유연성 도모

- 구현 클래스타입으로 선언하면, 그 클래스가 가진 불필요한 메서드 까지 노출됨.

  • 추후 인터페이스 타입으로 변경하려고 해도, 의존 코드를 다시 검토해야함.

- 예외. 인터페이스가 없는 클래스

  • 값 클래스: String, BigInteger
  • 인터페이스 없는 클래스 기반 프레임워크: 그래도, 구현클래스 보다는 추상클래스로 선언할것. java.io.OutputStream
  • 인터페이스에 없는 메서드가 필요한 경우: 구현클래스의 고유기능이 필요한 경우.
  • 요점. 가급적 덜 구체화된 클래스를 사용하여 선언하라.
