Effective Java 3Ed. item16.

아이템 16. public 클래스에서는 public 필드가 아닌 접근자 메서드를 사용하라

1. 퇴보한 클래스의 예

가끔 아래처럼 인스턴스 필드만 모아두는 것 외에 아무 목적이 없는 클래스를 작성하려 할 때가 있습니다.

이 클래스는 데이터 필드에 직접 접근할 수 있으니 캡슐화의 이점을 전혀 제공하지 못합니다.

2. public 필드가 나쁜 이유

public 필드를 직접 노출하면 다음과 같은 문제가 생깁니다:

  • API를 바꾸지 않고는 내부 표현을 바꿀 수 없다 (유연성 상실).
  • 불변식을 보장할 수 없다 — 클라이언트가 필드를 마음대로 바꿀 수 있다.
  • 필드에 접근할 때 부수 작업(로깅, 동기화 등)을 수행할 수 없다.

3. 올바른 방법: private 필드 + 접근자 메서드

public 클래스라면 필드를 모두 private으로 바꾸고, public 접근자(getter)와 변경자(setter) 메서드를 제공해야 합니다.

이렇게 하면:

  • 내부 표현을 언제든 바꿀 수 있다 (클라이언트는 메서드만 알면 됨).
  • setter에서 유효성 검사 등 부수 작업을 추가할 수 있다.
  • 불변식을 유지할 수 있다.

public 클래스가 필드를 공개하면, 그 필드를 사용하는 클라이언트가 생기고,
그 후에는 내부 표현을 바꾸기가 매우 어려워집니다.

4. 예외: package-private 또는 private 중첩 클래스

package-private 클래스 혹은 private 중첩 클래스라면 데이터 필드를 직접 노출해도 문제없습니다.

  • 패키지 외부 코드는 어차피 이 클래스에 접근할 수 없으므로, 표현을 바꿔도 패키지 안에서만 수정하면 됩니다.
  • private 중첩 클래스라면 그것을 감싼 클래스 안에서만 수정하면 됩니다.
  • 접근자 메서드를 강제할 때보다 오히려 코드가 더 간결하고 읽기 좋을 수 있습니다.

5. 불변 필드라면 덜 나쁘다 (하지만 여전히 좋지 않다)

public 필드가 불변(final)이라면, 직접 노출하더라도 그나마 덜 해롭습니다.
클라이언트가 값을 바꿀 수는 없으니 불변식은 보장됩니다.

그러나 이 경우에도:

  • API를 바꾸지 않고는 내부 표현을 바꿀 수 없습니다.
  • 필드 접근 시 부수 작업을 추가할 수 없습니다.

따라서 불변이라도 public 필드를 노출하는 것은 권장하지 않습니다.

6. 자바 플랫폼 라이브러리의 잘못된 예

java.awt 패키지의 Point와 Dimension 클래스는 public 필드를 직접 노출한 대표적인 반례입니다.

이미 수많은 코드가 이 필드에 직접 접근하고 있어서, 지금 와서 고칠 수가 없습니다.
특히 Dimension은 가변 필드를 노출한 탓에 성능 문제가 지금도 해결되지 않은 상태입니다.

이 클래스들은 “따라 하지 말아야 할 사례”로 유명합니다.

7. 핵심 정리

  • public 클래스는 절대 가변 필드를 직접 노출하지 마라.
  • 불변 필드라면 그나마 덜 해롭지만, 그래도 직접 노출하는 것은 권장하지 않는다.
  • package-private 클래스나 private 중첩 클래스는 필드를 직접 노출해도 된다.

Effective Java 3Ed. item15.

아이템 15. 클래스와 멤버의 접근 권한을 최소화하라

1. 핵심 원칙: 정보 은닉 (캡슐화)

잘 설계된 컴포넌트는 모든 내부 구현을 완벽히 숨기고, 외부와는 오직 API를 통해서만 소통합니다.
이를 정보 은닉(information hiding) 또는 **캡슐화(encapsulation)**라고 합니다.

정보 은닉이 중요한 이유:

  • 시스템 개발 속도 향상 — 여러 컴포넌트를 병렬로 개발할 수 있다.
  • 시스템 관리 비용 절감 — 컴포넌트를 빠르게 파악하고, 교체 부담이 줄어든다.
  • 성능 최적화에 도움 — 다른 컴포넌트에 영향 없이 특정 컴포넌트만 최적화할 수 있다.
  • 소프트웨어 재사용성 증가 — 독립적으로 동작하는 컴포넌트는 낯선 환경에서도 유용하다.
  • 큰 시스템 개발의 위험 감소 — 개별 컴포넌트 단위로 검증 가능하다.

원칙: 모든 클래스와 멤버의 접근성을 가능한 한 좁혀라.

2. 자바의 접근 제어 메커니즘

자바는 클래스, 인터페이스, 멤버의 접근성을 **접근 제한자(access modifier)**로 제어합니다.

접근 제한자는 private, package-private(기본값), protected, public 네 가지입니다.

접근 제한자 같은 클래스 같은 패키지 하위 클래스 어디서나
private O X X X
package-private (기본값) O O X X
protected O O O X
public O O O O

3. 클래스 수준의 접근 제한

톱레벨(top-level) 클래스와 인터페이스는 public 또는 package-private 두 가지만 가능합니다.

package-private으로 선언하면 좋은 경우

패키지 외부에서 쓸 일이 없다면, package-private으로 선언하세요.
그러면 API가 아닌 내부 구현이 되므로, 언제든 수정·교체·삭제할 수 있습니다.
반면 public으로 선언하면 하위 호환을 영원히 유지해야 합니다.

private static 중첩 클래스 활용

한 클래스에서만 쓰이는 톱레벨 클래스라면, 사용하는 클래스 안에 private static 중첩 클래스로 선언하세요.

4. 멤버(필드, 메서드, 중첩 클래스) 수준의 접근 제한

기본 원칙

  • 먼저 클래스의 공개 API를 신중히 설계하고,
  • 그 외 모든 멤버는 private으로 선언한다.
  • 같은 패키지 내 다른 클래스에서 꼭 필요한 경우에만 package-private으로 풀어준다.
  • protected와 public은 공개 API가 되므로 영원히 지원해야 한다.

private과 package-private은 내부 구현이라 공개 API에 영향을 주지 않습니다.
단, Serializable을 구현한 클래스는 의도치 않게 노출될 수 있습니다.

리스코프 치환 원칙과 접근 수준

상위 클래스 메서드를 재정의할 때, 접근 수준을 더 좁게 만들 수 없습니다.

인터페이스를 구현하는 클래스의 메서드는 반드시 public이어야 합니다.
(인터페이스 메서드는 기본적으로 public이기 때문)

5. public 클래스의 인스턴스 필드

public 클래스의 인스턴스 필드는 가급적 public이어서는 안 됩니다.

public 가변 필드를 갖게 되면:

  • 필드에 저장될 값을 제한할 수 없다 (불변식 보장 불가).
  • 필드 변경 시 다른 작업을 수행할 수 없다 (스레드 안전 확보 불가).

6. public static final 필드의 주의사항

상수라면 public static final 필드는 허용됩니다.
단, 반드시 기본 타입 값이나 불변 객체를 가리켜야 합니다.

배열은 절대 public static final로 두지 마라

길이가 0이 아닌 배열은 언제나 가변입니다.
public static final로 선언해도 배열의 내용은 외부에서 바꿀 수 있습니다.

해결 방법 1: 불변 리스트로 감싸기

해결 방법 2: 방어적 복사 반환

어느 방법이 더 좋은지는 상황에 따라 다릅니다.
클라이언트가 어떻게 사용하는지, 성능이 중요한지를 고려하세요.

7. Java 9의 모듈 시스템 (참고)

Java 9부터 모듈(module) 개념이 추가되었습니다.
모듈은 패키지의 묶음이며, 자신이 공개할 패키지를 module-info.java에 명시적으로 선언합니다.

  • public 클래스라도 해당 패키지가 모듈에서 공개되지 않으면 외부에서 접근 불가.
  • 모듈 내부 패키지끼리는 공유할 수 있지만, 외부 모듈에는 숨길 수 있다.

단, 모듈 시스템의 이 추가 접근 수준은 모듈 경로에 배치된 경우에만 적용됩니다.
일반 클래스패스에 놓이면 모듈 선언이 무시됩니다.

8. 핵심 정리

  • 접근성은 항상 최소화하라. 의도치 않게 API를 공개하지 않도록 주의하라.
  • public 클래스는 상수(public static final) 외에는 공개 필드를 가져서는 안 된다.
  • public static final 필드가 참조하는 객체는 반드시 불변이어야 한다.
  • 배열은 public static final로 두어서는 안 된다. 불변 리스트나 방어적 복사를 활용하라.

Effective Java 3Ed. item14.

아이템 14. Comparable을 구현할지 고려하라

책을 다시 읽고 다시 이해해라 !!

  • 아래 내용은 Claude가 요약한 내용.

1. Comparable 인터페이스란?

Comparable 인터페이스는 compareTo 메서드 하나만 가진 인터페이스입니다.

equals와 달리, compareTo는 순서 비교를 합니다. 즉, “나는 저 객체보다 크냐, 같냐, 작냐”를 판단합니다.

2. 왜 구현해야 하나?

Comparable을 구현하면 그 클래스의 인스턴스에 **자연적인 순서(natural order)**가 생깁니다.
자바 플랫폼의 거의 모든 값 클래스(String, Integer, BigDecimal 등)와 열거 타입이 이미 구현하고 있습니다.

구현하면 이런 것들이 자동으로 됩니다:

순서가 있는 값 클래스를 만들 때는 반드시 Comparable을 구현하세요.

3. compareTo의 일반 규약

compareTo는 세 가지 규약을 지켜야 합니다.
(sgn()은 부호 함수 — 음수면 -1, 0이면 0, 양수면 1)

규약 1. 대칭성

  • x가 y보다 크면, y는 x보다 작아야 한다.
  • x가 y에게 예외를 던지면, y도 x에게 예외를 던져야 한다.

규약 2. 추이성

  • x > y이고 y > z이면, x > z여야 한다.

규약 3. 일관성

  • x와 y가 같다고 판단되면, 다른 객체 z와의 비교 결과도 같아야 한다.

권고사항 (강제 아님)

  • compareTo가 0을 반환하면 equals도 true를 반환하는 것이 좋습니다.
  • 지키지 않으면 동작은 하지만, 컬렉션에서 이상하게 동작할 수 있습니다.

compareTo와 equals 불일치 예시 (BigDecimal)

4. compareTo 구현 방법

기본 원칙

상황 반환값
this < other 음수
this == other 0
this > other 양수

핵심: <, >같은 관계 연산자를 쓰지 마라

예전 코드처럼 직접 비교하면 정수 오버플로우 버그가 생길 수 있습니다.

올바른 방법 1: 박싱 타입의 정적 compare 사용

  • 중요도 순서대로 비교한다.
  • 앞 필드가 이미 다르면 바로 반환한다.

올바른 방법 2: Comparator 생성 메서드 활용 (Java 8+)

Java 8부터는 Comparator 인터페이스의 메서드 체이닝으로 우아하게 작성할 수 있습니다.

  • 코드가 간결하고 읽기 쉽습니다.
  • 단, 성능은 약 10% 정도 느릴 수 있습니다.

비교자 생성 메서드 종류

메서드 설명
comparingInt int 기준 비교
comparingLong long 기준 비교
comparingDouble double 기준 비교
comparing 객체 기준 비교
thenComparingInt 추가 int 기준 비교
thenComparing 추가 객체 기준 비교

5. extends vs implements의 규약 문제

compareTo 규약도 equals처럼 상속과 함께 쓰면 문제가 생깁니다.

새 필드를 추가한 서브클래스에서 규약을 지키면서 compareTo를 구현하는 것은 불가능합니다.
해결책은 **컴포지션(조합)**을 사용하는 것입니다.

6. 핵심 정리

  • 순서가 있는 값 클래스라면 반드시 Comparable을 구현하자.
  • compareTo에서 필드 비교 시 <, > 연산자 대신 Integer.compare() 같은 정적 메서드나 Comparator 생성 메서드를 사용하자.
  • compareTo와 equals가 일관되게 동작하도록 노력하자. (특히 TreeSet, TreeMap 등에서 중요)
  • 다중 필드 비교 시에는 가장 중요한 필드부터 비교하자.

아이템 12. toString을 항상 재정의하라

- Object 의 기본 toString은 단순히 클래스명@16진수해시코드 형태다.

  • 읽기 쉽고 유용한 정보를 보여주도록 재정의 하자
  • phoneNUmber라면 ‘phoneNumber: Henry=010-1234-5678’

- Collection 또는 정보량이 많을경우 Summary 를 보여주는것도 좋다

  • “맨해튼 전화번호부 (총 2299000개)

- 중요한 정보는 충분히 담아라.

  • 잘못된 예: “단언실패 : 기대값 {abc, 123}, 결과값 {abc, 123}”
  • toString 메세지를 보고 혼란 유발. (클래스타입을 추가하거나, 인스턴스 해시코드를 추가해야하지 않을까)

- 포멧을 명시하든 아니든, 그 의도를 명확히 밝혀라.

- toString이 반환한 값에 포함된 정보를 얻어올 수 있는 API 를 제공하라

  • toString의 반환값을 파싱해야 값을 얻을수 있는 상황을 만들지 말라
  • phoneNumber 라면 getAreaCode, getPrefix, getMemberNUmber 같은 접근자를 제공하자.

- 하위 컬랙션이 공유해야할 문자열 표현이 있는 추상클래스라면 toString을 재정의 해줘라.

아이템 10. equals는 일반 규약을 지켜 재정의하라

이번장은 내용이 많다. 여러번 다시 읽을 필요가 있다.

- equals를 재정의 하지 말아야할 이유

  • 각 인스턴스가 본질적으로 고유하다
  • 인스턴스의 ‘논리적 동치성’ 을 검사할 일이 없다. (Object의 기본 equals 만으로도 해결)
  • 상위클래스에서 재정의한 equals가 하위클래스에서도 딱 들어맞는다.
  • 클래스가 private 이거나, package-private이고 equals 메서드를 호출할 일이 없다.

- 그렇다면 equals 를 재정의 해야할 때는?

  • 객체식별성(두 객체가 물리적으로 같은가?)이 아니라, 논리적 동치성을 확인해야 하는데, 상위클래스의 equals가 논리적 동치성을 비교하도록 정의되지 않았을때.

- equals 메서드를 재정의할때 반드시 따라야할 일반규약

  • 반사성(reflexivity) : not null인 reference x에 대해(이하 생략) x.equals(x) = true 이다.
  • 대칭성(symmetry) : x,y에 대해 x.equals(y) = true 면 y.equals(x) = true 이다.
  • 추이성(transitivity) : x,y,x에 대해 x.equals(y) = true 이고 y.equals(z) = true 면 x.equals(z) = true 이다.
  • 일관성(consistency) : x,y에 대해 x.equals(y) 의 결과는 반복 수행되더라도 항상 true 이거나, 항상 false 이다.
  • null-아님 : x.equals(null) 은 false 이다.

- 양질의 equals 메서드를 구현하는 방법

  1. == 연산자를 사용해 입력이 자기 자신의 참조인지 확인한다.
  2. instanceof 연산자로 입력이 올바른 타입인지 확인한다.
  3. 입력을 올바른 타입으로 형변환한다.
  4. 입력객체와 자기 자신의 대응되는 핵심 필드들이 모두 일치하는지 하나씩 검사한다.

- 그리고, 테스트를 위한 AutoValue 프레임워크가 있다.

Effective Java 3Ed. item68.

아이템 68. 일반적으로 통용되는 명명 규칙을 따르라

[JLS, 6.1] 에 명명규칙이 잘 정리되어 있다.

- 패키지, 모듈이름

  • 조직의 인터넷 도메인이름의 역순
  • 각 요소는 대체로 8자 이내의 짧은 단어, 약자허용

- 클래스, 인터페이스

  • 대문자로 시작, 카멜케이스
  • 약자 지양 full단어
  • 객체를 생성할 수 있는 클래스의 이름은 보통 단수명사나 명사구 사용: Thread, PriorityQueue 등
  • 객체를 생성할 수 없는 클래스는 복수형명사로 : Collectors, Collections 등
  • 인터페이스는 클래스와 똑같이 짓거나 able , ible 로 끝나는 형용사 : Runnable, Iterable 등
  • 애너테이션은 규칙없이 다양

- 메서드, 필드

  • 클래스 명명규칙과 동일하지만 첫글자는 소문자
  • 상수필드는 full 대문자, 단어사이는 _ 언더바
  • 동사나 목적어를 포함한 동사구 사용 : append, drawImage
  • boolean 을 리턴하는 메서드는 보통 is , has 로 시작
  • boolean이 아닌경우 명사, 명사구, get속성, set속성 : size, hashCode, getTime, setTime 등
  • 객체 타입변경시 to목적타입 : toString, toArray 등
  • 객체의 내용을 다른 뷰로 보여주는 경우 as타입 : asList 등
  • 객체값을 원시타입으로 변경하는 경우 타입Value 형태로 : intValue, longValue
  • 정적팩터리 : from, of, valueOf, instance, getInstance, newInstance, getType, newType

- 지역변수

  • 소문자. 약어 가능

타입 매개변수

  • 보통 한문자 대문자로 표현
  • T:타입, E:컬랙션의 원소, K,V:맵의 키와 밸류, X:예외, R:메서드의 반환타입, U,V,T1,T2..:그외 임의타입

Effective Java 3Ed. item67.

아이템 67. 최적화는 신중히 하라

- 최적화 격언 세가지

  1. 그 어떤 핑계보다 효율성 이라는 이름아래 행해진 컴퓨팅 죄악이 더 많다.(심지어 효율을 높이지도 못하면서)
  2. (전체의 97% 정도인) 자그마한 효율성은 모두 잊자. 섣부른 최적화가 만악의 근원이다
  3. 최적화를 할때는 다음 두가지 규칙을 따르라.
  • 첫번째, 하지마라
  • 두번째, (전문가 한정)아직 하지마라

섣부른 최적화는 자칫 견고한 구조설계를 파괴하고도 높은 성능개선을 이루지 못한다는 것.

이하 내용의 상세 설명은 이해될때 추가할것.

- 빠른프로그램 보다는 좋은 프로그램을 작성하라

- 성능을 제한하는 설계를 피하라

  • 특히 변경이 어려운 요소들. 컴포넌트간/시스템간 외부소통 프로토콜. API, 네트워크, 영구 저장데이터포멧 등

- API를 설계할때 성능에 주는 영향을 고려하라

- 성능을 위하여 API를 왜곡하지 마라

- 각각의 최적화 시도 전후로 성능을 측정하라

- 알고리즘부터 재검토하라

Effective Java 3Ed. item66.

아이템 66. 네이티브 메서드는 신중히 사용하라

- 자바 네이티브 메서드란?

  • native 키워드를 사용하여, java 가 아닌 C, C++ 같은 다른 프로그래밍언어(네이티브코드) 로 구현된 함수를 java 코드에서 직접 호출하는 메서드.

- 목적

  1. 레지스트리등 플랫폼 특화기술
    Java -> JNI -> OS API (Win32 API, POSIX) -> 하드웨어/커널
  2. 레거시 C, C++ 라이브러리 활용
  3. 성능 크리티컬한 부분을 C로 최적화 (요즘엔 vm 성능이 극적으로 향상되어, 유명무실.)

- 단점

  1. 메모리 안전성 파괴
  2. 플랫폼 독립성 상실
  3. 디버깅 난이도 급상승
  4. GC와의 상호 작용 복잡성

- 대안

  1. Panama API로 JNI 완전 대체
  2. 성능 측정후 결정하는 원칙
  3. GraalVM Native Image로 네이티브 필요성 제거

- JNI는 Java의 안전망에 구멍을 뚫는다. 현대 Java는 그 구멍을 하나씩 메우고 있다.

Effective Java 3Ed. item65.

아이템 65. 리플렉션보다는 인터페이스를 사용하라

- 리플렉션이란? java.lang.reflection

  • 프로그램이 자기자신의 구조를 런타임에 조사하고 조작하는 기능

- 리플렉션의 단점

  1. 컴파일 시점에 타입 검사 불가
  1. 장황하고 복잡한 코드: Exception만 붙여도 6종.
    ClassNotFoundException NoSuchMethodException IllegalAccessException
    InstantiationException InvocationTargetException ClassCastException …
  2. 성능저하 - 아래 과정을 매번 거침.
    invoke() 호출 -> 접근권한 검사(isAccessible?) -> 파라미터 타입 검증
    -> 오토박싱 (primitive -> Object) -> 실제 메서드 디스패치 -> 결과 언박싱

- 리플렉션의 활용

  • 컴파일시에는 알수 없고, 런타임에 존재하지 않을수도 있는 다른 클래스, 메서드의 의존성 판단시
  • 버전이 여러개인 외부 클래스의 의존성 선택.

- 대안

  • 생성만 리플렉션, 생성 이후에 사용할때는 인터페이스나 상위클래스로 형변환해서 사용.
